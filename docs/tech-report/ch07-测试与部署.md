# 第 7 章 测试与部署

## 7.1 三层测试策略

| 层次 | 数量 | 工具 | 覆盖什么 | 不覆盖什么 |
|---|---|---|---|---|
| 后端单元/集成 | **160** | pytest + httpx | 业务函数、接口契约、数据库行为 | 界面表现 |
| 前端冒烟 | **79** | 自研 runner + 极简 DOM 垫片 | 渲染结构、状态迁移、数据一致性、算法 | 真实浏览器排版 |
| 线上端到端 | **43** | 自写验证脚本（httpx） | 部署后是否真的可用 | 代码分支细节 |

**为什么需要第三层**：前两层都在本地，跑通不代表线上可用。线上第一次部署时只有 API、没有前端页面（端口 80 空着），本地测试全绿——**这类问题只有端到端验证能发现**。

## 7.2 后端：202 个测试

| 测试文件 | 用例数 | 主要断言 |
|---|---|---|
| `test_dedupe.py` | 34 | 四级判定的优先级、版本号比较、扫描件识别、边界（同名不同论文） |
| `test_retrieval.py` | 30 | 混合检索、RRF 融合顺序、IDF 闸门、配额裁剪、降级链 |
| `test_bm25.py` | 27 | 中文 2-gram、IDF 计算、BM25 打分公式、空查询 |
| `test_chunking.py` | 21 | 700/120 切分、标题携带、超长句、无标点文本 |
| `test_pdf_parser.py` | 20 | 标题层级推断、参考文献切分、扫描件判定、质量分 |
| `test_api_papers.py` | 15 | 上传/列出/解析/删除的接口契约与错误码 |
| `test_paper_service.py` | 13 | 事务边界、去重落盘、文件名归一化 |

**一个刻意的设计**：业务层测试不启动 HTTP 服务，直接构造数据库会话调用函数。这让 202 个测试在 **36 秒内**跑完——如果每个用例都走 HTTP，同样的覆盖要 3 分钟以上。

## 7.3 前端：98 个冒烟用例

前端零依赖（见 3.3 ②），没有 Jest/Vitest，自写了一个 runner：用极简 DOM 垫片加载 18 个脚本，逐条断言。

| 类别 | 覆盖内容 |
|---|---|
| 渲染 | 每个视图都能渲染出关键结构（`.disc-item`、`[data-action="discover-ingest"]` 等），空状态与错误态都有 |
| 状态 | 切换视图后 `route` 正确；删除论文会清理阅读目标；问答范围从多篇切回单篇会收敛 |
| 数据一致性 | 论文 id 唯一、分块都能对应到真实论文、正文引文编号都有对应参考文献条目 |
| 算法 | 去重相似度、BM25 排序、CSV 解析（含引号包裹的逗号） |

**两条经验**：
1. **断言要抓选择器而不是字符串**：「代码写了但元素没出来」这类缺陷，只有 `querySelector` 断言能抓住；
2. **垫片有局限要写进注释**：极简 DOM 在 `innerHTML` getter 里会把文本节点重新序列化并再转义（`&quot;` → `&amp;quot;`），个别文本断言需对"渲染函数原始输出"而非 DOM 断言，否则会误报。

## 7.6 部署与四个真实踩坑

部署形态：阿里云 ECS 单机、`systemd` 托管、端口 8000、数据在 `backend/data/`；更新用一条脚本（打包 git bundle → scp → 服务器 pull → 重启 → 健康检查）。

| # | 踩的坑 | 现象 | 根因与修复 |
|---|---|---|---|
| 1 | **线上只有 API，没有页面** | 打开域名 404，本地全绿 | 只注册了 `/api/v1` 路由，没挂 StaticFiles。修复：`app.mount("/", StaticFiles(..., html=True))` **且必须最后注册**，否则会吞掉 API 路由 |
| 2 | **部署后浏览器仍是旧页面** | 代码已更新，界面没变 | StaticFiles 只发 ETag/Last-Modified，浏览器按"启发式缓存"直接复用旧文件。修复：对 `.html/.js/.css` 加 `Cache-Control: no-cache, must-revalidate` |
| 3 | **嵌入额度耗尽后问答整体拒答** | 检索返回 `mode=empty` | 向量路异常 + BM25 被 IDF 闸门跳过，两条路同时为空。修复：`bm25_fallback` 回退并声明置信度（详见 5.4.1） |
| 4 | **充值后仍报额度耗尽** | 账户有余额，接口仍 400 | 两处原因叠加：① 控制台开着"免费额度用完即停"；② API Key 是 `sk-ws-` 前缀的**业务空间专属 Key**，而免费额度按业务空间分别统计。修复：切到对应空间关闭该开关 |

**坑 4 的教训最值得记**：云服务的额度错误要读完整错误码。我们最初把 `degraded_reason` 截断到 200 字符，正好切掉了 `AllocationQuota.FreeTierOnly` 之后那句"disable the use free tier only mode"的关键提示，白白多花了一轮排查。

## 7.7 部署与更新流程

| 脚本 | 作用 |
|---|---|
| `start.ps1` | 本地一键启动：建虚拟环境依赖检查 → 启动 uvicorn → 打开浏览器 |
| `deploy/update_online.ps1` | 线上更新：检查工作区干净 → 打包 bundle → scp → 服务器 pull → 重启 → 健康检查 |
| `deploy/verify_online.py` | 更新后验收：43 项检查，失败即报错 |

**设计取舍**：服务器访问 GitHub 不稳定，因此用 git bundle 传输而非直接 pull；脚本检测到工作区有未提交改动会**主动中止**，避免线上与本地不一致——这个"拦一下"的设计救过我们两次。

## 7.8 评测：30 题 gold set

单元测试证明"代码按预期跑"，但回答不了"答得准不准"。为此单独做了一套评测，
和 `pytest` 刻意分开：前者打真实模型、分钟级、有成本；后者必须离线、秒级、可重复。

### 7.8.1 数据集

`docs/eval/gold.json`：**25 道可答题 + 5 道不可答题**。

* 可答题覆盖库内主要论文的关键事实（BLEU 值、层数、作者、数据集来源等），
  每题给出 2~3 个"必须出现"的关键词，用于自动判定是否命中；
* 不可答题是库内完全没有的领域（量子计算、AlphaFold、5G、医学、中文分词），
  用来检验"不知道就说不知道"，而不是编造。

### 7.8.2 指标定义

| 指标 | 定义 | 回答什么问题 |
| --- | --- | --- |
| Recall@K | 期望关键词是否出现在检索前 K 段中 | 检索得着吗 |
| 引用准确率 | 引用片段中含期望事实的比例 | 引用对得上吗 |
| 可答率 | 回答正文命中关键词且至少一条引用 | 真的答出来了吗 |
| 拒答准确率 | 库内没有的问题是否明确拒答 | 会不会瞎编 |

### 7.8.3 实测结果

线上环境（20 篇论文 / 1116 页 / K=16）连跑两次：

| 指标 | 第 1 次 | 第 2 次 |
| --- | --- | --- |
| Recall@16 | 96.0% | 96.0% |
| 引用准确率 | 82.3% | 84.4% |
| 可答率 | 80.0% | 84.0% |
| 拒答准确率 | 100% | 100% |
| 平均耗时 | 2.2 s | 2.0 s |

**两个如实记录的现象**：

1. `a03`（第六作者是谁）检索未命中，但回答仍答对且引用准确 —— 说明
   "检索命中"不是"答对"的必要条件，两个指标必须分开看；
2. 有 4 题检索到了却零引用（a05 / a11 / a16 / a24），属**过度保守**：
   模型在上下文里找不到可直接引用的句子就拒答。方向没错，但仍有优化空间，
   这也是两次运行引用准确率浮动 2pp 的来源。

报告由 `deploy/eval_gold.py` 自动生成，见 `docs/eval/report.md`。
