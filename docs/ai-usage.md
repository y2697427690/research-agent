## 二、参与范围总览

项目共 45 次提交，按阶段划分如下：

| 阶段 | 模块 | AI 参与方式 | 人的工作 |
| --- | --- | --- | --- |
| P0 | 配置、日志、错误、数据库、健康检查 | 逐段讲解后给出代码 | **手敲录入**、逐条验证 |
| P1 | 上传、去重、版本识别 | 逐段讲解后给出代码 | **手敲录入**、手写测试 |
| P2 | PDF 结构化解析 | 讨论策略后给出代码 | **手敲录入**、用真实 PDF 反复调参 |
| 前端基线 | 8 个页面、80 项自测 | 逐段讲解后给出代码 | **手敲录入**、设计界面与交互 |
| 部署 | 一键部署脚本、更新脚本、线上验证脚本 | **AI 直接写入文件** | 服务器上执行、按报错反向定位问题 |
| P3 | 分块、BM25、向量检索、RRF 融合 | **AI 直接写入文件** | 运行真实数据验证、提出改进方向 |
| P4 | RAG 问答、引用校验、SSE 流式 | **AI 直接写入文件** | 端到端实测、发现并推动修复质量问题 |
| P8 | 前端联调（API 层、适配层、数据桥） | **AI 直接写入文件** | 浏览器实测、决定取舍 |

**分界点**：项目前期（P0~P2、前端基线）由人逐行手敲录入，
以保证对每一行代码的理解；后期（部署、P3、P4、P8）因工作量与交付时间压力，
改为 AI 直接写入文件 + 人工运行验证。

## 三、提示策略（怎么用 AI）

### 1. 先讲原理，再要代码

每个模块开始前，先要求讲清「这个模块解决什么问题、为什么这样设计、有什么备选方案」，
确认理解后再要代码。例如 P3 开始前先讲清：

- 什么是嵌入（把文本变成向量，语义相近则向量相近）
- 为什么有了嵌入还要 BM25（精确术语 vs 语义改写，两者互补）
- 为什么不引入向量数据库（万级分块下 numpy 矩阵乘法十几毫秒即可）

### 2. 要求给出可验证的检查点

不接受「这样应该可以」，要求每一步都有可执行的验证方式：

- 写完 BM25 建索引 → 要求给出分词结果与倒排表的验证命令
- 写完引用校验 → 要求给出「正常 / 越界 / 编号为 0」三组用例
- 写完 SSE → 要求给出「首字延迟 vs 总耗时、token 时间段数」的判定标准

### 3. 用真实数据反驳 AI 的判断

AI 给出的结论必须用真实数据检验。例如：

- AI 声称「RRF 融合效果更好」→ 用 4 个问题做对照实验，实测目标章节排名
- AI 声称「分块无问题」→ 打印「区域 → 页码」列表，发现 1788/2332 个块丢失章节归属
- AI 声称「过滤器不误伤」→ 逐个打印候选块的特征值，发现 2 个表格被误删

### 4. 遇到矛盾先怀疑输入

当报错信息与事实矛盾时（例如「明明有可用版本却说找不到」），
先逐字节检查输入，而不是怀疑工具。本项目因此在 `>=0.09` 与 `>=0.0.9`
一个字符的差异上定位到根因。

## 四、质量保障：AI 产出如何被验证

**不采信 AI 的自我评价，只采信可执行的证据。**

| 验证手段 | 规模 |
| --- | --- |
| 后端单元与接口测试 | **158 个用例**，覆盖解析、去重、分块、检索、问答 |
| 代码规范检查（ruff） | 零告警，规则配置中包含理由注释 |
| 前端冒烟测试 | **80 项**，覆盖 8 个页面的结构与状态流转 |
| 真实 PDF 回归 | 15 页论文 / 541 页书籍 / 扫描件三类，断言具体数值 |
| 线上端到端验证 | `deploy/verify_online.py`，**34 项**检查，退出码可用于 CI |
| 浏览器实测 | SSE 逐段到达、跨语言检索、拒答行为 |

**AI 产出被发现并修复的典型错误**（均由实测暴露，非人工 review 发现）：

| 错误 | 发现方式 |
| --- | --- |
| 分块章节归属未沿后续页继承，书籍 77% 的块丢失章节 | 打印「区域 → 页码」列表 |
| 参考文献过滤器误删含引用的表格 | 打印 12 个候选块的特征值做对比 |
| 重新解析会丢弃已付费的向量 | 线上验证脚本的 embedded 计数归零 |
| 认证失败被无意义重试 3 次 | 失败耗时 3~4 秒异常偏高 |

## 五、人与 AI 的分工边界

**由人做出的决策**（AI 只提供备选与数据）：

- 技术选型：FastAPI、SQLAlchemy、PyMuPDF、百炼嵌入、numpy 而非 FAISS
- 产品取舍：P9 提前部署、P8 优先于 P5、中英对照延后到 P7
- 部署方案：IP + 端口而非域名备案、systemd 而非 Docker
- 拒绝引入的方案：向量数据库、LangChain、重排模型（理由见技术文档附录 B）

**由 AI 完成的工作**：

- 代码实现、文档初稿、部署脚本、排错方案建议
- 实验设计与对照数据整理

**产品运行时的 AI 使用**（与开发辅助无关，需另行说明）：

- 嵌入模型（阿里云百炼 text-embedding-v1，1536 维）用于语义检索
- 对话模型（DeepSeek deepseek-chat）用于 RAG 答案生成
- 两者均通过环境变量配置，密钥不出现在仓库中

## 六、已知风险与应对

| 风险 | 应对 |
| --- | --- |
| 对 AI 生成的代码理解不深，答辩时无法解释 | 每个模块都保留了「为什么这样设计」的说明，写在代码注释与 `docs/architecture.md` 中；核心技术判断（RRF、引用校验、IDF 过滤）均有对照实验数据支撑 |
| AI 生成的代码可能存在未覆盖的边界问题 | 用真实文档（标准论文、长篇书籍、扫描件）做回归，测试覆盖到边界条件 |
| 提交历史中 AI 参与部分不易区分 | 本文档按阶段列明参与方式；提交信息中记录了问题现象与修复理由，便于追溯 |
