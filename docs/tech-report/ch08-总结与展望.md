# 第 8 章 总结与展望

## 8.1 完成情况

本项目实现了一个面向个人科研阅读的 AI 助手，覆盖"上传 → 解析 → 检索 → 问答 → 阅读 → 翻译 → 引用分析 → 写作"的完整链路，并在三条线上同时可验证：

| 维度 | 结论 |
|---|---|
| 功能覆盖 | 34 个可验收条目中已实现 19 条、部分实现 6 条、未实现 9 条（第 2 章 2.2） |
| 需求验收 | 需求原文给出的 5 个单篇问题**全部通过**；多篇问题中 BERT 对比题通过 |
| 工程质量 | 后端 160 测试、前端 79 冒烟、线上 43 项验证，ruff 零告警 |
| 线上可用 | 20 篇真实论文、4784 分块全部向量化，`http://47.96.97.141:8000/` 可直接访问 |

## 8.2 三条经验

**① 降级链必须真的能降下去。**
我们写了"向量不可用 → 降级 BM25"，但另一处"信息量过滤器"把 BM25 也关了，两个各自合理的设计叠加成"完全不可用"。**只有在线上真的让依赖挂掉，才会发现这类问题。** 之后我们把"故意让某条路失效"写进了测试。

**② 提示词约束不可靠，关键行为要落到后处理。**
"能答就直接答"写进提示词也照样不执行；真正管用的是服务端的确定性处理（剥离假拒答、拒答重试、引用编号校验）。**模型负责生成，服务端负责把关。**

**③ 参数会随规模失效，而且失效是静默的。**
片段数在 8 篇论文时 12 条够用，库扩到 15 篇就不够了——不报错，只是答案变差。所以把标准问题固化成回归脚本，比"感觉还行"可靠得多。

## 8.3 已知局限

按影响程度排序（完整清单见第 2 章 2.4）：

| 局限 | 影响 | 改进路径 |
|---|---|---|
| 表格结构、图表、公式、扫描件 OCR 未实现 | 中：影响"解析粒度"打分 | 接入 Camelot / PaddleOCR / 视觉大模型 |
| **引用角标与参考文献的双向跳转缺失** | **高**：需求明文点名，数据已就绪 | 前端锚点 + 回跳栈，约 1 天 |
| 划词翻译为术语表实现 | 中：细粒度翻译不可用 | 选中即译 + 缓存，避免逐词调用 |
| 导出 Markdown / HTML / 原位 PDF 未实现 | 中：需求提到输出可读性 | 1 天 |
| 定期追踪 arXiv、推荐、自动综述未实现 | 中：模块四、五各缺一半 | 调度器 + 相关性计算 + 多篇聚合 |
| 写作助手的四项目前是本地模板 | 中：未接大模型 | 接入模型做语义化生成 |
| 单用户模型 | 低 | 多用户需加隔离与协同过滤 |

## 8.4 后续路线

优先补需求明文点名的能力：**P0**（约 3 天）引用双向跳转、划词翻译接模型、导出 Markdown/HTML；**P1**（约 7 天）表格/公式/OCR 解析增强、领域综述与 Future Work 探索；**P2**（约 6 天）定期追踪 arXiv、引用含金量筛选、写作助手接模型；**P3**（约 1 周）多用户与协同过滤。

## 8.5 结语

这个项目的核心判断是：**大模型的能力已经足够，真正缺的是"敢让用户核对"的工程约束。**

所以我们在每个环节都留了可验证的钩子——引用编号能点回原文、检索降级会明说质量下降、解析质量低会标"需校对"、未实现的能力写在页面上。这些做法不增加功能数量，但让系统从"演示能跑"变成"用户敢用"。

**能力边界写清楚，比把功能目录写满更接近工程实践。**
