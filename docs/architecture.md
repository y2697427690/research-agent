## 附录 B：技术选型记录

> 记录每个技术决策的「为什么」，用于第 4.1 节「选型理由」。

| 决策点 | 选择 | 备选 | 理由 |
| --- | --- | --- | --- |
| Web 框架 | FastAPI + Pydantic v2 | Flask / Django | 官方技术栈推荐；原生 async 支持 SSE 流式；Pydantic 自动校验并生成 API 文档 |
| 数据库驱动 | SQLAlchemy 2.0 async + aiosqlite | 直接用 sqlite3 | ORM 抽象层让将来切换 PostgreSQL 只改连接串 |
| 配置管理 | pydantic-settings | os.getenv | 自动类型转换与校验；API Key 用 SecretStr 包装，避免日志泄露 |
| 错误处理 | 自定义 AppError + 统一处理器 | 直接抛 HTTPException | 前端只需处理一种错误格式；未处理异常对外不暴露堆栈 |
| PDF 解析 | PyMuPDF | pypdf / 手写解析 | 官方推荐工具；可同时获取文字、坐标、字号、表格结构 |
| 图论分析 | NetworkX | 手写 numpy 实现 | 官方技术栈推荐；内置 PageRank、介数中心性等算法 |
| 代码规范工具 | Ruff | flake8 + isort + black | 一个工具覆盖 lint 与格式化，速度极快；配置中显式忽略 B008（FastAPI 的 `Depends()` 属于该规则的误报）与 N818（异常类名不加 Error 后缀更简洁），并在配置里注明理由 |
| 分块策略 | 章节感知 + 句子边界 | 固定长度滑窗 | 固定长度会把句子、公式、表格从中间切断，且丢失章节信息导致无法标注出处；论文版面本身是结构化的，用结构比忽略结构准确 |
| 关键词检索 | 自实现 BM25 | Elasticsearch / rank_bm25 库 | 规模只有万级分块，自实现约 200 行且可完全解释；引入 ES 会带来一个额外的服务进程与运维成本 |
| 向量检索 | numpy 暴力检索 | FAISS / Qdrant | 万级分块下向量矩阵约 120 MB，一次检索为一次矩阵乘法（约 3000 万次乘加），numpy 十几毫秒完成。向量数据库带来的毫秒级收益远小于部署复杂度；分块数到十万级再迁移，对外接口不变 |
| 融合算法 | RRF（只用名次） | 分数加权求和 / 各自归一化后相加 | BM25 分数无上界而余弦相似度在 [-1,1]，量纲不可比。归一化相加会抹掉「分数是否密集」的信息；RRF 与任何打分体系兼容，无需调权重 |
| 嵌入模型 | 阿里云百炼（OpenAI 兼容端点） | OpenAI / 本地 BGE-M3 | 部署在国内服务器，OpenAI 直连不可用；本地模型需约 2 GB 的 torch，2 核 2G 服务器跑不动；百炼有免费额度且国内直连 |
| 向量维度 | 运行时探测，不硬编码 | 配置项写死 1024/1536 | 换模型即换维度，硬编码会导致静默算出错误的相似度；探测后还可对不一致的分块做告警与跳过 |

## 附录 A：踩坑记录

> 开发过程中实际遇到并解决的问题。这部分是一手材料，用于第 4 章「优化策略」与第 6 章「测试与部署」。

- SQLite 默认不开外键约束，必须在连接时 PRAGMA foreign_keys=ON，
  否则外键写了等于没写（实测：插入不存在的 pid 竟然成功）
- .gitignore 里 ! 反向排除必须紧跟被排除规则，
  否则 .env.* 会把 .env.example 一并吃掉
- FastAPI 内置 /docs 与 /redoc 从 cdn.jsdelivr.net 加载 swagger-ui / redoc 资源，
  该 CDN 在部分网络下 TLS 连接被重置（WinError 10054），表现为
  「页面标题正确但内容白屏」（HTML 返回 200，静态资源加载失败）。
  对策：下载静态资源到 app/static/ 自托管。已实测：关闭代理后仍可正常打开。
- GitHub 推送报 `Recv failure: Connection was reset` 未必是被阻断：
  本次重试后成功，属偶发网络抖动。判断方法：分别测 443 与 22 端口，
  并重试 2~3 次后再下结论。长期方案是配置 SSH 密钥（已配置，免密免代理）。
- 单元测试直接暴露了 4 个肉眼难以发现的缺陷：旧版 arXiv 编号不支持下划线、
  Windows 下 basename 不识别正斜杠、元组漏解包、扫描件判定顺序错误。
  这类缺陷靠人工点击界面很难覆盖，是引入 pytest 的直接收益。
- FastAPI 的文件上传接口依赖 python-multipart，它是 fastapi 的可选依赖，
  只装 `fastapi` 时不会自动带上；缺失时接口在运行时报
  `RuntimeError: Form data requires "python-multipart" to be installed`。
  对策：写入 pyproject.toml 主依赖。教训：代码正确不等于能跑起来，依赖也是代码的一部分。
- 测试用内存 SQLite 时必须使用 StaticPool：`sqlite:///:memory:` 是「每条连接一个
  独立实例」，建表连接与接口连接看到的不是同一个库，表现为 `no such table`。
  同时应在 import app.main 之前替换 db.session 的 engine，
  让 lifespan 的建表也走测试库，从而完全不触碰真实的 data/app.db。
- PATCH 接口必须用 `payload.model_dump(exclude_unset=True)` 取字段，
  否则客户端只传部分字段时，未传字段会被 None 覆盖，导致已有数据被清空。
- Windows PowerShell 5.1 不支持 `Invoke-RestMethod -Form` 与
  `System.Net.Http.MultipartFormDataContent`（需 PowerShell 7+）。
  做接口端到端验证时改用 Python 脚本（httpx）或 curl.exe 更可靠。
- 中文输出在 PowerShell 5.1 控制台会显示为乱码，执行 `chcp 65001` 可正常显示；
  这属于终端编码问题，不影响程序输出的实际内容。
- PDF 内置书签（`doc.get_toc()`）是目录最可靠的来源：实测官方两篇论文与
  541 页书籍都带书签，能直接给出「层级 / 标题 / 页码」三级结构，
  比从字号推断准确得多。解析策略应以「有书签用书签、无书签才回退」为第一原则。
- 标题提取必须排除竖排侧边文字：arXiv 论文左侧水印
  "arXiv:1706.03762v1 [cs.CL] 12 Jun 2017" 字号 20.0，比真正的标题（17.2）还大，
  其 bbox 为 (11,216,38,560) —— 宽 27、高 344。判据用「高度 > 宽度 × 2」即可排除。
- 标题行常与页码等文字合并成一行（如 "1 Introduction 1"、"Bibliography 464"），
  因此标题识别不能只用「整行相等」的正则，应改为「包含 + 长度限制」。
- 摘要边界不能只靠行距：实测摘要末行与下一节标题只差 31pt，
  必须把「遇到章节标题即停」作为主判据，行距阈值（约 18pt）作为辅助。
- 置信度评分必须对文本量敏感：合成的小样本 PDF（每页约 30 字符）会得到
  quality≈0.34 并被判为需校对，而真实论文（每页 800+ 字符）为 1.0。
  这一点已写成测试用例，确保评分不是常量。
- 分块的「页 → 章节」映射必须沿后续页继承。首版只在章节起始页赋值，
  其它页一律记为 None，结果 541 页书籍 2332 个块中有 1788 个丢失章节归属。
  **这个 bug 从总数（2304 块）上看不出来**，只有把「区域 → 页码」列表打出来
  才能发现「每章只有起始页有标题」。教训：统计量正常不代表数据正确，
  要抽查结构本身。
- 参考文献过滤踩了「过度过滤」的坑：首版仅用「≥3 个 [n] 编号 + ≥3 个年份」判断，
  把论文 Table 3/4 也删掉了——表格里同样有引用标记与年份。
  补救方式不是调参猜阈值，而是打印 12 个候选块的「数字占比 / 平均词长 /
  长词比例」做对比：表格 0.30 与 0.11，文献 0.05~0.09，分界线清晰。
  最终判据加入「数字占比 < 0.10」与「长词比例 ≥ 0.35」。
  原则：过滤阈值宁保守勿激进——漏掉几个噪声块只是轻微干扰，
  误删表格是丢失真实内容。
- 版本约束 `>=0.09` 与 `>=0.0.9` 是不同版本：PEP 440 会把 `0.09` 规范化为 `0.9`。
  python-multipart 的版本是 0.0.x 系列（最高 0.0.32），因此 `>=0.09` 永远无解。
  报错信息 `No matching distribution found for python-multipart>=0.09` 极具误导性：
  后面列出的可用版本看似包含满足条件的版本，肉眼也极易把 `0.09` 读成 `0.0.9`。
  排查方法：用同一约束单独 `pip install` 该包，若单独能装而集体装失败，
  说明项目文件里的约束写法有问题，应逐字节检查该行。
  **核心教训：当报错信息与事实矛盾时，先怀疑输入，而不是怀疑工具或网络。**
- 国内云服务器部署有三个环境陷阱，都不是代码问题：
  1. 服务器访问 GitHub 被阻断，`git clone` 会长时间卡住 → 改为本地
     `git bundle` + scp 上传，服务器从 bundle 拉取
  2. PyPI 直连不稳，报 `No matching distribution found`（实为下载失败），
     且阿里云镜像自带的 `/etc/pip.conf` 会覆盖用户配置 →
     用 `--index-url` 显式指定清华源优先级最高
  3. `pip config list` 可能显示多个 index-url（内网镜像 + 用户配置），
     内网镜像索引不完整，是上述误导性报错的来源之一
- PowerShell 5.1 解析 .ps1 脚本时按 GBK 读取无 BOM 的 UTF-8 文件，
  中文注释会变成乱码并报大量「意外的标记」语法错误。
  对策：脚本必须存为 UTF-8 **带 BOM**，并使用 CRLF 换行。
- 部署目标（服务器）应保持为仓库的纯镜像。若在服务器上直接改过文件
  （例如用 sed 临时修依赖版本），后续 `git pull` 会因「本地改动将被覆盖」中止。
  正确做法是所有修复在开发机完成并提交，服务器只拉取与重启；
  更新脚本中先 `git reset --hard HEAD` 再 pull（.env 与 data/ 已被忽略，不受影响）。
- `uvicorn --reload` 默认监视**整个 backend 目录**，其中包含 `backend/data/`。
  而上传、解析、翻译都会写 `data/app.db`——文件一变就触发重启，
  正在进行的请求被掐断，前端表现为「无法连接后端服务」，
  同时健康检查又完全正常，极易误判成服务没启动。
  对策：`--reload-dir app`，只监视代码目录。写数据不再触发重启。
  **教训：热重载的监视范围要与「数据目录」明确分开。**
- 前端报「无法连接后端服务」时，不一定真是服务没起。本项目遇到两种原因：
  1. 热重载把请求掐断（见上一条）
  2. CORS 来源不匹配：`localhost` 与 `127.0.0.1` 在浏览器中是**两个不同来源**，
     只白名单其中一个时，用另一个地址打开会让所有请求被拦，
     而浏览器给出的也是网络错误，与「服务未启动」在控制台里无法区分。
     排查方法：看 Console 的报错文案——CORS 会明确写出
     `blocked by CORS policy` 与缺失的 `Access-Control-Allow-Origin` 头。
- **「检索成功」不等于「回答成功」**。前端引用面板原先只有「引用到的片段」一份数据，
  模型在资料不足时拒答，面板就显示「本次回答未检索到相关片段」。
  而实测该问题检索返回了 7 个片段、作者名单就在第 1 条——
  是模型判断资料不足以支撑答案，并非检索故障。
  把两类失败合并显示，会让排查方向整个走偏。
  对策：把「检索到的片段」与「模型引用到的片段」分开保存与展示，
  面板明确区分「没有检索到任何片段」与「检索到 N 段但模型未引用」。
  **教训：RAG 的失败至少分三类——没召回、召回但相关性低、模型判断资料不足。
  只有把三类分别暴露，抗幻觉才是可验证的。**
- **用「默认锁定范围」兜底，会制造「看起来对、其实错」的回答**。
  问答范围默认取文库列表第一篇，用户问另一篇论文时，检索只在这一篇里找：
  运气好是拒答，运气不好是**答了另一篇论文的同类信息**——
  例如问《Attention Is All You Need》第 6 作者，却答出《CLIP》的第 6 作者 Sandhini Agarwal，
  格式、引用、角标全部正常，只有论文是错的。这类错误比拒答危险得多，
  因为用户会把错误结论当成原文事实。
  对策：**能用问题内容确定范围的就不要用默认值兜底**——
  对问题做标题归一化包含匹配，命中哪篇就把哪篇并入检索范围；
  确实需要默认值时，界面上必须把「当前范围」写清楚。
  注意扩范围只应影响检索，不应当作「用户要做对比」的信号：
  对比模式改按调用方显式指定的论文数判断，
  否则单篇问题会得到「各篇论文在……维度上」这种对比式回答。
- **元信息类问题的资料要固定给，不能靠语义检索碰运气**。
  论文首页块包含标题、作者名单、机构与摘要开头，是「第 N 作者是谁」「在哪个机构」
  的唯一来源；但它未必排在语义检索前列（实测 6 条命中里 5 条是注意力机制正文）。
  对策：每篇命中论文的首页块作为固定片段加入上下文，与语义检索互补。
  同类问题还有参考文献：参考文献区在分块时被刻意过滤（避免污染正文检索），
  因此「列出关于 X 的参考文献」永远只能拒答；对策是问题命中参考文献类关键词时，
  从 citations 表（抽取引用关系时已落库）取文献列表追加为一段资料。
- **问答温度取 0，而不是 0.2**。同一问题、同一份资料，0.2 时模型时而作答、
  时而拒答，同一份代码前后两次验证得到相反结论，导致「能力是否达标」无法判断。
  这类抖动在需要复现的评测场景里是不可接受的。
  顺带测得：片段数 top_k 需要随语料规模增长——论文库 6 篇（1064 块）时 8 条够用，
  扩到 8 篇（1709 块）后 8 条已命不中「训练 Base 模型用了多少 GPU」所需的 5.2 节，
  12 条才稳定；再往上（16、20）答案不再变化，只白耗 token。
  **教训：片段数不是常数，它随语料规模变化，需要按实测重新标定。**

### 一次「拒答」牵出的七个问题（2026-10-21，线上同步）

用户问「Layer Normalization 在 Transformer 中放在什么位置」，线上直接拒答。
顺着往下拆，发现这条链路上有七个独立问题，每一个单独看都「像在正常工作」：

1. **前端从未真正部署**。服务器上没有 nginx，80 端口空着，只有 uvicorn 在 8000；
   仓库里的 `nginx.conf` 只是模板，从未执行。于是「仓库里前端更新了、但用户看不到」
   这件事一直没被发现。对策：后端直接把 `frontend/` 挂到根路径
   （`mount("/")` 必须最后注册，否则会兜住 `/docs` 与 `/api`），复用已开放的 8000 端口。
2. **验证脚本只测 API，所以上面那条一直没暴露**。原 34 项检查全部打接口，
   页面 404 也能全绿。对策：新增第 11 节「前端页面」，检查根路径返回页面、
   `index.html` 含主题初始化脚本、三个静态资源可访问且非空、`app.js` 含主题切换逻辑。
   **原则：验证必须覆盖「用户实际打开的那个地址」。**
3. **默认锁定范围会制造「看起来对、其实错」的回答**（问答范围默认取文库第一篇论文）。
4. **「问题点名论文就扩展检索范围」把技术名词当成了论文标题**（上一轮修复引入的回归）：
   库里有篇论文标题就叫《Layer Normalization》，于是「问 LN 在 Transformer 里的位置」
   被收窄成「只搜 LN 那一篇」——而该篇 2016 年发表、早于 Transformer，必然拒答。
   对策：该规则只在**调用方已指定范围**时生效；全库检索时直接跳过，
   因为全库本就能搜到任何论文，再「扩展」只会把范围缩小。
5. **单篇论文垄断候选**。同一问题，向量检索前 20 条全部来自同一篇
   （标题与问题语义几乎一致，但解析质量仅 0.44、章节全丢、块内容残缺），
   其它论文一条都进不来。对策：按论文限流从「仅多篇对比启用」扩展到「全库检索也启用」，
   每篇最多 3~4 条。
6. **关键词检索的「信息量」判据太窄**。原实现只看排名第一那条命中块匹配到的词，
   它可能恰好只匹配 `layer` 这类高频词，于是整条关键词路被判无信息量而跳过。
   对策：取前 5 条命中中出现过的最强 IDF 词。
7. **参考文献片段的构造有四个叠加缺陷**：先按顺序截断 80 行（目标条目排不进来）、
   只从「检索命中的论文」里找（真正的条目在没被命中的那篇文献表里）、
   条目自带编号与片段编号冲突（`[1] [1] …`）、把**问题点名论文自己**的文献表排在最前
   （它当然不会引用自己，模型据此判「资料不足」）。
   对策：按问题中的英文词筛选条目、查找范围改为指定范围或全库、
   剥离条目自带编号并统一用 `-` 前缀、排除问题点名论文自身的文献表、短条目优先。

**方法论收获**：这一轮没有一个问题能靠「读代码」或「看日志告警」发现——
它们都需要**把链路上的中间数据打出来看**（检索命中了哪些论文、文献片段实际长什么样、
前端资源返回了几字节）。因此排查 RAG 类系统时，
应当在每一层都保留可观测的输出，而不是只验证最终的答案对错。
