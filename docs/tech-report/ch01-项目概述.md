# 第 1 章 项目概述

## 1.1 项目背景

科研人员读一篇论文的时间成本，远比"读不完"更具体：为了确认一句话里的数字，往往要把 30 页 PDF 从头翻到尾；用通用大模型总结论文时，模型会给出格式漂亮但**出处不明**的结论，逐条回原文核对的时间比直接读还长；当同一方向积累到十几篇论文时，引用关系散落在各自的参考文献里，很难判断哪篇是奠基工作、哪篇只是衍生。

本项目针对这三件事分别给出可验证的答案：

| 痛点 | 具体表现 | 本项目的应对 |
|---|---|---|
| **找** | 想确认「训练 Base 模型用了多少 GPU」，需要通读全文 | 混合检索（关键词 + 向量）定位到段落级片段 |
| **核** | 大模型总结会编造，无法判断哪句话有原文支撑 | 抗幻觉三层机制：无命中即拒答、强制引用编号、服务端校验编号 |
| **连** | 十几篇论文的引用关系散落在参考文献里 | 抽取引用关系并构图，用入度 / PageRank / 连通分量识别基石论文 |

## 1.2 项目目标

构建一个**面向个人科研阅读**的 AI 助手，覆盖"上传 → 解析 → 检索 → 问答 → 阅读 → 翻译 → 引用分析 → 写作"的完整链路，并且做到：

1. **每个结论都能溯源**：回答里的每个编号都能点回原文段落；
2. **没把握就拒答**：检索不到或在资料中找不到依据时，明确说"资料中没有"，而不是编造；
3. **界面上的数字都能追到数据库**：不展示无法追溯的统计，宁可移除；
4. **工程上可验证**：后端单元测试、前端冒烟测试、线上端到端验证三层覆盖。

## 1.3 目标用户与使用场景

面向**个人研究者、研究生与高年级本科生**。典型使用场景：

- **精读单篇**：上传一篇论文，反复追问方法细节、超参数、实验设置；
- **横向对比**：上传同一方向的多篇论文，让系统分述各家做法并指出承袭与差异；
- **文献综述起步**：先看引用图谱确定主干文献，再逐篇问答；
- **非母语阅读**：中英对照阅读，代码与公式保留英文原文。

## 1.5 当前实现范围（如实说明）

本项目在比赛周期内完成，功能覆盖情况如下表。**未实现的部分同样列出**，并在第 8 章给出改进路径——我们认为把边界讲清楚，比含糊带过更符合工程规范。

| 能力 | 状态 |
|---|---|
| PDF 上传 / 批量 / 内容去重 / 版本识别 | 已实现 |
| 文本层 PDF 解析（标题、作者、摘要、章节树、参考文献） | 已实现 |
| 分块 + 向量化 + 混合检索（BM25 + 向量 + RRF 融合） | 已实现 |
| 单篇问答 / 多篇跨文献对比 / SSE 流式输出 | 已实现 |
| 中英对照阅读 + 整篇翻译（分块缓存） | 已实现 |
| 引用关系抽取 + 引用图谱（入度 / PageRank / 连通分量） | 已实现 |
| arXiv 关键词检索 + 一键下载入库并解析 | 已实现 |
| 扫描件 OCR | 未实现（仅标记"需校对"） |
| 表格 / 公式 / 图表的提取与渲染 | 部分（表格提取能力弱，公式按纯文本） |
| 正文引用角标与参考文献的双向跳转 | 未实现（数据已就绪） |
| 划词翻译接真实模型 | 部分（当前为术语表实现） |
| 导出 Markdown / HTML / 原位排版 PDF | 未实现 |
| 引用含金量筛选、定期追踪、多用户推荐 | 未实现 |
